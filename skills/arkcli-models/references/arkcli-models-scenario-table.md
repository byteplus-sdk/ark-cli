# Models scenario recommendation table (curation layer / highest priority for intent ranking)

> **Prerequisite:** Read [`../arkcli-shared/SKILL.md`](../../arkcli-shared/SKILL.md) first to understand authentication, global parameters, and safety rules.
> **Snapshot alignment:** 2026-06. The "Version" column is a **curated snapshot**, not the source of truth. **Always use the complete model ID returned in real time by `arkcli models search`**. See the JOIN protocol below.

## What this table solves

Model search is not a recall problem; it is a ranking problem. The local cache contains **all models**, so every query has 100% recall. The difficult part is **accurate ranking**. Naming heuristics (generation / tier / update_time) can only guess capabilities from model names; they cannot determine whether "this model is suitable for translation or Agent tasks". What is missing is a **labeling system**.

This table is that labeling system: a manually curated `scenario label → recommended model` mapping that fixes the "intent → model" step. It is the **highest-priority signal for intent ranking**, above naming heuristics, but recommendations must be verified against the left table (local cache) before adoption.

## Usage rules

- The Agent recalls recommended models based on "scenario label + recommended model description".
- Recommended model descriptions include version differences, common requirement terms, legacy model aliases, and upgrade guidance to improve retrieval.
- When the user explicitly specifies a third-party, open-source, or historical model, return to `arkcli models search` and **do not forcibly replace it**.
- This table serves only "find a model by intent" (the search path). **Enumeration / inventory / statistics use `arkcli models list` without this table's reranking.**

## JOIN / verification protocol (scenario table ⨝ full local cache)

**Core principle: the scenario table supplies intent, while `arkcli models search` supplies facts. Versions/full IDs in the table are only starting points; use the real-time search response for matches.**

**Layer boundary (do not mix layers): this table is the "model marketplace selection layer". Its data source is always `models search` (catalog), and it provides catalog-recommended model names.** "Whether the current profile can call it and the exact callable ID" belongs to the downstream availability layer (`resources list` → `models get` → `+gen`/`+chat`; arkcli-gen is implemented) and is **outside this table's responsibility**. Pure selection questions ("find/choose a model") use only `models search`; do not query `resources list`. Descend to resources list to resolve the current profile's actual ID only when the user truly wants to generate/invoke. Example: image-generation selection returns `dola-seedream-5-0` (catalog name); a plan profile may actually invoke `dola-seedream-5-0-pro`, which downstream `+gen` resolves.

```
① User intent → match scenario label               (use requirement terms in "Recommended model description" to improve matching)
② Take the row's "Default recommended model" and derive the family stem (for example, Dola-Seed-2.0-lite → seed-2-0-lite)
③ arkcli models search <family stem>               ← verify facts against the left table (required; cannot be skipped)
   ├─ exact   family matches and version is consistent → concatenate <name>-<primary_version> and rank it first
   ├─ drift   family matches but version differs       → use the actual version returned by search (already sorted by gen/time; take the top)
   │                                                    and say "recommendation snapshot X, current Y"
   ├─ bare    match with primary_version=None (voice/audio) → stop at marketplace discovery: only state that it is discoverable; do not concatenate a version or pass it downstream
   └─ miss    no match for the family stem             → table ID may be stale; search again using a scenario term or shorter stem
④ Add 2–3 alternative candidates from search results with the same modality
⑤ User names a third-party/open-source/historical model (Seedream 4.5, glm…) → skip this table, search directly, and do not forcibly replace it
```

### Key boundaries (derived from actual testing; must read)

- **Do not pass the table's full ID directly to `+chat` / `+gen`, and do not add suffixes to model names from memory**. The actual image-generation model is `dola-seedream-5-0` (**without the `-lite` suffix; no variant with `-lite` exists in the cache, and an exact query returns no items**). Such naming drift recurs. **Search by family stem, always trust the returned result, and do not append suffixes such as `-lite` / `-pro` yourself.**
- **Search tolerates DisplayName**: `Dola-Seed-2.0-lite` (dots and case included) also matches `seed-2-0-lite`, but the **family stem (lowercase with hyphens) is the most reliable** and should be the preferred search keyword.
- **The six voice/audio entries follow the bare path and currently support only marketplace discovery in arkcli**: they appear in the models catalog but have `primary_version=None` and no enrichment (ctx/lifecycle are empty). After a match, state directly that the bare name is discoverable in the marketplace, but do not try to concatenate a version number and do not pass it to `+chat` / `+gen` / `+deploy` / `usage` / `pricing` / `onboard`. For arkcli, marketplace discovery does not mean callable, Endpoint-creatable, price-queryable, or usage-queryable.
- **Avoid `-internal` variants**: search may return internal variants such as `seed-2-0-lite-internal`; do not recommend them to users.
- **Lifecycle**: when a candidate is `Retiring`, proactively tell the user it is being retired and find a newer version in the same family (consistent with the main SKILL).
